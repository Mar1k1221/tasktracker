## Дополнительные наблюдения

### Локальные коллекции

В `TaskService` используются локальные коллекции:
- `HashMap` внутри метода `getStatistics()`;
- `HashSet` внутри метода `save()`.

В `TaskController` создаётся локальный `ArrayList`.

Эти коллекции создаются внутри вызовов методов, поэтому каждый запрос получает собственные экземпляры. Они не являются общими полями Singleton-бинов.

### Важное замечание о final

Модификатор `final` запрещает переназначить ссылку на объект, но не делает сам объект неизменяемым или потокобезопасным.

Например:

`private final List<String> recent = new ArrayList<>();`

Ссылка `recent` не изменится, но содержимое списка можно менять. Если несколько потоков будут одновременно вызывать `recent.add()`, возникнет проблема потокобезопасности.

### Вывод

В проверенных классах не обнаружено собственных общих изменяемых полей, которые могли бы создавать гонку данных при одновременной обработке запросов.

Основные поля — это неизменяемые ссылки на зависимости Spring, логгеры и конфигурационные значения.

При этом `final` у ссылок на зависимости сам по себе не гарантирует потокобезопасность внутренних объектов. Она зависит от конкретной реализации этих объектов.

**Отдельно:** проверка не включает `RequestIdFilter` и другие классы с `@Component`, код которых ещё не был рассмотрен.

## Задание 3. Проверка общего изменяемого состояния

Для эксперимента в TaskService добавлено поле:

private final List<String> recent = new ArrayList<>();

В методе создания задачи каждый запрос добавлял название задачи в этот список.

Результаты теста:

| Показатель | Результат |
|---|---:|
| Параллельных запросов | 50 |
| Успешных HTTP 201 | 50 |
| Ожидаемых элементов | 50 |
| Фактических элементов | 43 |
| Потерянных записей | 7 |

Вывод:

ArrayList не потокобезопасен при одновременной записи из нескольких потоков.
Несмотря на то что все 50 задач успешно сохранились в PostgreSQL,
в общем списке потерялись 7 записей.

Модификатор final защищает ссылку от переназначения,
но не защищает содержимое коллекции от конкурентного изменения.
## Задание 5. Поведение 201-го одновременного запроса

По умолчанию Tomcat использует максимум 200 рабочих потоков.

Настройка находится в application.properties:

server.tomcat.threads.max=200

Если все 200 потоков заняты обработкой запросов,
201-й запрос не создаёт новый поток, а ожидает освобождения
одного из существующих потоков.

При исчерпании очередей и лимитов соединений новые подключения
могут быть отклонены или завершиться по тайм-ауту.

Дополнительные параметры:
- server.tomcat.threads.max-queue-capacity — размер очереди задач;
- server.tomcat.max-connections — максимум соединений;
- server.tomcat.accept-count — очередь входящих подключений.

Вывод: ограничение в 200 потоков не означает, что приложение
может принять только 200 соединений. Оно ограничивает количество
одновременно работающих потоков обработки запросов.
